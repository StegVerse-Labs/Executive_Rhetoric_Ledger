**Model / reviewer:** Kimi (Moonshot AI agent), 2026-10-27

### 1. The question, as the author has now framed it — adopted as the manuscript's central research question

> *Why are some companies apparently charging for failed usage while others incorporate mechanisms that prevent it?*

This is the right question, and it is the strongest framing the discussion has produced, for three reasons:

1. **It is comparative, not accusatory.** It asks why mechanisms differ across providers selling computationally near-identical products. No provider is declared right or wrong; divergence itself is the object of study.
2. **It is answerable in layers.** Parts can be answered from the evidence already assembled (Zone 1/2); the remainder decomposes into explicit, testable hypotheses rather than suspicion.
3. **It inverts the burden correctly.** Once a deployed mechanism proves feasibility, the analytical burden shifts from "must providers remediate?" to "what explains non-adoption?" — a question about design and policy choices, which is exactly where this issue's evidence lives.

The word *apparently* is doing precise work: per round 7, charge treatment in the silent-error class on rate-limit plans is **DERIVED** (structural basis), not ledger-OBSERVED. The manuscript should keep that qualifier until instrumented data exists.

### 2. What the assembled evidence already answers

**The divergence is real and located.** The coverage matrix now documents: one provider with a published automatic non-deduction rule for system-detected failure plus a published dispute path; providers with no published rule at all; and a three-month archived failure series in the silent-error class remediated only by customer corrective prompting (correction-cost transfer). The divergence is not hypothetical.

**The sharpest pattern in the whole record — divergence is largest where detection is cheapest:**
- *System-detected failure* (crash, error string, no valid result): detection is technically trivial — the system already knows it failed, which is why one provider's automatic path exists. Yet published policies diverge most here. Difficulty cannot explain this cell.
- *Silent model error* (D3): detection is genuinely hard for everyone, and **no** provider covers it automatically — convergence, not divergence.

**DERIVED conclusion:** the limiting factor in the divergent cell is not technical capability. When detection is cheap and remediation is demonstrably deployed by a competitor, non-adoption is a *policy/business/design choice*, not an engineering constraint. This is the evidence-based form of the author's "computer code" point, and it is the manuscript's strongest single analytical result.

### 3. The explanatory hypotheses the question generates — to be tested, not asserted

The manuscript should enumerate candidate explanations for non-adoption, each falsifiable:

| # | Hypothesis | Class | How tested |
|---|---|---|---|
| H1 | **Actuarial absorption** — failures are priced into entitlement sizes instead of remediated per-event | DERIVED candidate | Policy-text capture at time of sale: is the failure-loss disclosed? If undisclosed, absorption may still exist but the transparency gap stands |
| H2 | **Disclosure lag** — a mechanism exists internally but was never published | Open | Provider disclosure; instrumented trials detecting restoration that no policy describes |
| H3 | **Unit-geometry friction** — rate-limit plans make "restoration" value hard to define, discouraging any rule | DERIVED candidate | Compare published rules by geometry (stock vs rate-limit); note Kimi operates *both* geometries (monthly pool + Kimi Code 5-hour limit) and still publishes a failure rule — which weakens H3 |
| H4 | **Gaming exposure** — automatic remediation invites induced-failure abuse; providers stay silent rather than build verification gates | DERIVED candidate | Abuse-resistance analysis (already a v0.6 section); note the 👎 verification gate shows one deployed answer |
| H5 | **Competitive insufficiency** — remediation UX has not yet been a market differentiator, so no pressure to build | PROJECTED | Market/behavioral evidence; outside this issue's data |

The author's question is answered by whichever of these survives testing — and the record already undercuts H3 (geometry doesn't prevent publishing) and supplies H4's counterexample (a verification-gated dispute path is deployed). What no hypothesis can claim, post-feasibility-proof, is *inability*.

### 4. What "apparently overcharging" means precisely, for the manuscript

Defined relative to the competitor baseline: a customer is charged for compute that delivered none of the represented service, on a plan where (a) no published rule restores it, (b) no restoration was observed, and (c) the customer's only remedy — corrective prompting — consumes further entitlement. Each element now has an evidence status in this issue: (a) OBSERVED (coverage matrix), (b) OBSERVED-absence in the archived series, (c) OBSERVED (Case Study C records). The composite term "apparent overcharging" may be used in the manuscript **only with that decomposition attached** — it is a summary of evidence statuses, not a finding of fact about any ledger.
