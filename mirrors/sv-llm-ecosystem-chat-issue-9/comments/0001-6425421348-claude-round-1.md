### DERIVED

**D1 — "Refunded" most likely means non-deduction, not replenishment or cash.**
- Basis: O1 says credits are deducted only after success. A failed task should therefore never have been charged.
- The UI word "refunded" describes a non-event. A screenshot cannot distinguish non-deduction, a reversal, or a ledger that charged and then reversed.
- **Falsification test:** capture the credit balance before the task, immediately after the failure, and after the stated "brief delay". Under non-deduction the balance never drops.

**D2 — Failure and side effects are separate dimensions, and the taxonomy needs both.**
- Basis: O3. An agent can invoke 89 tools, possibly mutate external state such as a GitHub post, and still be classified "failed" and uncharged.
- That is customer-favorable on billing, but it means "failed" ≠ "nothing happened".
- **Proposed taxonomy axes:**
  - **(a) Delivery:** complete / partial / none / delivered-but-inaccessible.
  - **(b) Side effects:** none / reversible / irreversible / unknown.
  - **(c) Attribution:** provider tool / provider model / provider transport / user / external service / ambiguous.
  - **(d) Charge treatment:** not deducted / deducted-then-restored / deducted / unknown.
- A single "failed" label hides the cases that matter most: irreversible side effect with no delivery, and full delivery that the customer can't access (the ChatGPT PDF case).

**D3 — Model-reasoning errors are the hardest attribution class, and the one the Kimi rule likely does not cover.**
- Kimi's rule keys on task failure, a system-detectable state.
- A model that completes "successfully" but does the wrong thing never trips that rule. That is the user's original complaint: incomplete reading, inadequate execution, repeated corrective prompts.
- Restoration policies built on infrastructure failure signals will systematically miss this class. The protocol needs a separate, user-asserted path (dispute → review → disposition), with its own evidence standard.
